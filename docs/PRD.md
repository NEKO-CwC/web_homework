# Minimal Mall 在线商城 PRD

> UI 改造权威边界：自 2026-05-29 起，商城化 UI、导航展示、角色入口和三端页面壳的后续改造以 `docs/SHOPPING_UI_REDESIGN_SOT.md` 为唯一事实来源。本文档继续作为业务功能、数据能力、权限规则和课程验收范围的权威文档。

## 1. 文档定位

本文档是本仓库推进设计、开发、测试和部署的单一产品准则。除非后续明确更新本文档并记录版本变化，否则功能范围、角色权限、业务状态、技术约束、验收标准均以本文档为准。

项目目标是完成一个淘宝模式的在线商城课程大作业，覆盖顾客前台、商家中台、管理员后台三类使用场景，并以现有 UI 原型的极简商城风格作为最终界面方向。

## 2. 背景与目标

### 2.1 背景

课程题目要求实现在线商城，顾客模块包括登录、浏览、注册会员、购物车、购买商品、虚拟付费、确认收货、虚拟运单、评价、退换货申请；商家模块包括注册申请开店、店铺和商品管理、商品销售、退换货及物流管理；管理员模块包括商家管理、系统维护和首页管理。

现有原型 `design/minimal-commerce-ui-prototype.html` 已定义产品信息架构、页面布局、视觉风格和主要交互反馈。研发实现必须延续该原型的角色划分、导航结构和极简视觉语言。

### 2.2 产品目标

- 完成课程要求的全部核心功能，形成可演示、可部署、可验收的在线商城系统。
- 使用 monorepo 组织顾客前台、商家中台、管理员后台和共享包，减少重复代码。
- 使用 Docker Compose 编排本地和服务器部署环境，保证数据库、应用和迁移流程可复现。
- 使用 Next.js、shadcn/ui、PostgreSQL、Prisma 构建完整前后端闭环。
- 通过 CI 连接指定服务器，拉取最新代码并重新部署，形成稳定交付流程。

### 2.3 成功标准

- 作业图片中列出的顾客、商家、管理员功能均可在系统中操作演示。
- 三端页面与原型的信息架构一致，主要页面均具备真实数据读写能力。
- 购物主链路可完整跑通：注册/登录 -> 浏览商品 -> 加入购物车 -> 虚拟支付 -> 商家发货 -> 虚拟运单 -> 确认收货 -> 评价/售后。
- 商家入驻主链路可完整跑通：申请开店 -> 管理员审核 -> 商家维护店铺和商品 -> 商品在前台展示。
- 管理员可管理商家、首页内容、关键系统配置，并可查看系统状态和审计记录。
- 代码通过 lint、typecheck、测试和 Docker Compose 构建。

## 3. 范围

### 3.1 本期范围

- 顾客前台：账号、商品发现、商品详情、购物车、结算、虚拟支付、订单、虚拟物流、评价、售后、个人资料。
- 商家中台：开店申请、店铺资料、商品发布与上下架、商品图片、订单处理、虚拟运单生成、售后处理、销售统计。
- 管理员后台：平台总览、商家审核与状态管理、首页 Banner/广告位管理、系统配置、虚拟支付/运单服务状态、审计日志。
- 技术工程：monorepo、共享 UI、共享 Prisma schema、Docker Compose、CI 远程部署、基础测试和种子数据。

### 3.2 非目标

- 不接入真实支付网关、真实物流接口和真实短信服务。
- 不做复杂推荐算法、优惠券系统、分销系统、直播带货等扩展电商能力。
- 不实现真实营业执照 OCR 或第三方资质认证，资质文件仅做上传、预览和审核状态流转。
- 不追求大规模高并发架构，本项目以课程验收和完整业务闭环为优先。

## 4. 用户与角色

### 4.1 顾客

顾客浏览商品、管理购物车、下单、完成虚拟支付、查看订单和虚拟运单、确认收货、评价商品、申请退换货，并维护个人资料和默认地址。

### 4.2 商家

商家先提交开店申请。审核通过后进入商家中台，维护店铺信息、发布商品、上传商品图片、管理库存和上下架状态，处理订单发货、虚拟运单、售后申请。

### 4.3 管理员

管理员负责平台治理，审核商家入驻，启用/冻结商家，管理首页内容和广告位，维护系统配置，查看虚拟支付、虚拟运单、安全配置和审计日志。

### 4.4 权限规则

| 角色 | 允许访问 | 禁止访问 |
| --- | --- | --- |
| 游客 | 首页、商品列表、商品详情、登录注册、商家申请入口 | 购物车结算、订单、商家中台、管理员后台 |
| 顾客 | 顾客前台全部个人功能、商家申请 | 其他顾客数据、商家中台、管理员后台 |
| 商家 | 自己店铺、自己商品、自己订单、自己售后 | 其他商家数据、管理员后台 |
| 管理员 | 后台管理、商家审核、首页管理、系统维护 | 直接修改用户密码明文、越权暴露敏感配置 |

## 5. 信息架构

### 5.1 顾客前台

- 首页 / 商品发现：商品卡片、分类筛选、搜索入口、精选商品、申请成为商家入口。
- 商品详情：商品图片、标题、价格、店铺、库存、评分、参数、加入购物车、立即购买。
- 购物车：商品列表、数量修改、删除、金额汇总、结算入口。
- 结算 / 虚拟支付：收货信息、虚拟支付方式、金额确认、支付结果反馈。
- 订单 / 虚拟物流：订单状态、虚拟运单号、物流时间线、确认收货、评价/售后入口。
- 评价 / 退换货：选择订单、评分、评价内容、售后类型、原因、说明和凭证。
- 注册登录 / 个人信息：账号注册、登录、昵称、默认地址、联系方式。

### 5.2 商家中台

- 商家开店申请：店铺名称、经营类目、店铺介绍、资质图片、提交审核。
- 商品 / 店铺管理：店铺资料、商品编辑、图片上传、价格、库存、上下架状态。
- 销售 / 物流 / 售后：订单列表、待发货统计、虚拟运单生成、售后处理、销售额统计。

### 5.3 管理员后台

- 平台总览：入驻商家数、待审核商家数、广告位数、系统健康度、待办事项。
- 商家审核管理：审核通过、驳回、启用、冻结、复核商家。
- 首页 / 广告位管理：Banner 标题、图片、跳转链接、分类入口、专题广告位。
- 系统维护：会员注册配置、商家入驻配置、首页缓存刷新、虚拟支付/运单状态、安全巡检、审计日志。

## 6. 设计准则

### 6.1 视觉基线

- 视觉方向沿用原型的 Minimal Mall：干净背景、低噪音商品卡、清晰信息层级、克制阴影和圆角。
- 组件库使用 shadcn/ui，所有表单、弹窗、按钮、表格、Tabs、Toast、Dialog 优先基于 shadcn 组合实现。
- 样式 token 应复用原型中的方向：`surface`、`muted`、`accent`、`success`、`warn`、`danger`、`motion-fast/base/slow`。
- 页面必须响应式适配桌面和移动端。移动端导航可折叠，表格可横向滚动或转为列表。
- 商品前台避免过度促销堆叠，卡片只保留图片、标题、一句卖点、价格、主操作。
- 商家和管理员界面偏工作台风格，强调表格、筛选、状态标签、批量操作和清晰反馈。
- 所有关键操作必须有 Toast、Dialog 或页面状态反馈，包括加入购物车、支付成功、申请提交、生成运单、审核通过、保存首页配置。

### 6.2 必须落地的页面视觉清单

最终 UI 必须覆盖原型中的 14 个页面。实现可以按三端拆成不同 Next.js 应用，也可以按路由分组拆分，但页面能力不得缺失。

| 原型页面 | 建议路由 | 页面必须展示的视觉结构 |
| --- | --- | --- |
| 首页 / 商品发现 | `/` | Hero、商品卡片网格、分类/筛选入口、购物车入口 |
| 商品详情 | `/products/[id]` | 大图区域、商品信息卡、价格、评分、参数、加入购物车、立即购买 |
| 购物车 | `/cart` | 购物车商品行、数量步进器、小计、合计、结算摘要 |
| 结算 / 虚拟支付 | `/checkout` | 收货表单、支付方式、履约步骤、支付按钮 |
| 订单 / 虚拟物流 | `/orders` | 订单表格/列表、状态标签、运单号、物流时间线 |
| 评价 / 退换货 | `/after-sale` | 评价表单、售后表单、订单选择、原因选择 |
| 注册登录 / 个人信息 | `/account` | 登录/注册 Tabs、资料表单、默认地址 |
| 商家开店申请 | `/merchant/apply` | 入驻申请表、资质上传、审核流程 |
| 商家商品 / 店铺管理 | `/merchant/products` | 商品编辑表单、图片上传、在售商品列表、状态标签 |
| 商家销售 / 物流 / 售后 | `/merchant/orders` | 指标卡、订单表格、生成运单、售后处理入口 |
| 管理员平台总览 | `/admin` | 指标卡、待办事项、跳转操作 |
| 商家审核管理 | `/admin/merchants` | 商家审核表格、通过、驳回、冻结/复核状态 |
| 首页 / 广告位管理 | `/admin/home` | Banner 预览、配置表单、广告位状态 |
| 系统维护 | `/admin/system` | 服务状态卡、系统配置项、审计/安全入口 |

验收时不得只实现空白占位页。每个页面必须至少包含真实数据或 seed 数据驱动的内容、主要操作按钮、加载/空状态/错误状态之一。

### 6.3 交互逻辑基线

下列交互是 UI 验收的硬性基线。若某项功能对应的后端能力尚未完成，前端也必须提供明确的禁用态或错误态，不允许出现无反馈的“死按钮”。

| 场景 | 必须验证的 UI 行为 |
| --- | --- |
| 全局导航 | 点击导航可切换到对应页面；移动端导航可打开、关闭；当前页面有明确 active 状态 |
| 全局搜索 | 输入关键词后显示搜索中、无结果或结果列表反馈；快捷键提示不得遮挡输入框 |
| 加入购物车 | 商品卡和详情页点击后购物车数量更新，并出现 Toast 成功反馈 |
| 购物车数量 | 加减数量后行小计和结算合计同步更新；低于 1 或超过库存时按钮禁用或显示错误 |
| 结算支付 | 表单校验失败时字段级报错；虚拟支付成功弹出 Dialog 或跳转订单详情 |
| 确认收货 | 仅运输中订单可点击；点击后按钮进入 loading/disabled，成功后状态更新并出现评价入口 |
| 提交评价 | 已收货订单可评价；成功后 Toast 反馈；重复评价必须禁用或提示 |
| 发起售后 | 提交后出现成功 Dialog，售后记录进入商家中台待处理列表 |
| 商家申请 | 资质和必填字段缺失时阻止提交；提交成功后进入待审核状态 |
| 发布商品 | 必填字段、价格、库存、图片校验明确；发布后商品出现在前台或商家商品列表 |
| 生成运单 | 待发货订单点击后生成 `VL-0000-0000` 格式运单，订单状态变为运输中 |
| 商家审核 | 管理员通过/驳回后商家状态立即更新；驳回必须填写原因 |
| 首页配置 | 保存 Banner/广告位后顾客首页展示更新内容，并有 Toast 成功反馈 |
| 系统维护 | 配置开关、刷新缓存、服务状态卡均有明确成功、失败或禁用反馈 |

### 6.4 组件状态覆盖

每个可复用 UI 组件必须覆盖以下状态，开发和测试不得只验证 happy path。

- 表单组件：默认、focus、输入中、校验失败、提交中、提交成功、提交失败、禁用。
- 按钮组件：默认、hover、focus-visible、loading、disabled、danger。
- 表格/列表：有数据、空数据、加载中、错误、分页、移动端窄屏。
- 卡片组件：商品正常、缺货、下架、图片缺失、长标题、长价格。
- 状态标签：成功、警告、危险、强调、普通。
- 弹窗与 Toast：打开、关闭、Escape 关闭、点击遮罩关闭、连续触发不重叠。

### 6.5 视觉质量门禁

UI 迭代必须满足以下视觉门禁，任何一项不满足都不能视为完成。

- 不出现文字重叠、按钮文字溢出、表格内容遮挡、卡片高度跳变导致布局错乱。
- 桌面端 `1440x900`、平板端 `768x1024`、移动端 `390x844` 三个视口均可完成顾客核心链路。
- 页面首屏必须保留清晰主视觉和主操作，不能只有空表格或空白说明文字。
- 商品图、Banner、上传占位图必须稳定占位，加载前后不得造成明显布局位移。
- 前台页面保持轻量商品展示，不允许堆叠过多运营色块、促销标签或强对比背景。
- 中台和后台保持工作台密度，优先表格、筛选、状态标签和批量操作，不做营销式大 Hero。
- 所有交互控件必须有可见 focus 状态，键盘可达。
- 普通正文和按钮文字颜色必须达到 WCAG AA 对比度；危险操作必须有明确视觉区分。
- 动效只用于页面切换、Toast/Dialog、按钮反馈和必要状态变化；必须尊重 `prefers-reduced-motion`。

### 6.6 自动化校验要求

后续实现必须提供面向 UI 的自动化验证脚本。脚本名称可按实际工程调整，但 README 必须写明等价命令。

- Playwright 或等效 E2E 测试必须覆盖：登录、浏览商品、加入购物车、结算支付、确认收货、评价/售后、商家申请、管理员审核、商家发货、首页配置。
- UI 截图验证必须至少覆盖 3 个视口：`390x844`、`768x1024`、`1440x900`。
- 每个核心页面必须至少产出一张验收截图，建议保存到 `artifacts/ui-checks/` 或 CI artifact。
- E2E 测试必须断言关键可见文本、按钮状态、Toast/Dialog、URL/页面跳转、订单/运单/审核状态变化。
- 对有上传能力的页面，测试必须覆盖合法文件、非法文件类型、超大文件或模拟上传失败。
- 对权限页面，测试必须覆盖未登录、错误角色、正确角色三类访问结果。

### 6.7 人工验收清单

每次完成 UI 相关迭代后，执行 agent 必须在交付说明中列出以下结果：

- 修改了哪些页面和组件。
- 对照 `design/minimal-commerce-ui-prototype.html` 保留了哪些视觉结构，若有偏离说明原因。
- 已验证的视口尺寸。
- 已验证的交互清单。
- 自动化测试命令和结果。
- 未覆盖或仍有风险的 UI 项。

## 7. 技术与架构约束

### 7.1 技术栈

| 层级 | 选型 | 约束 |
| --- | --- | --- |
| Monorepo | pnpm workspace 或 Turborepo | 顾客、商家、管理员应用共享包管理 |
| 前端框架 | Next.js App Router | 使用 TypeScript，优先 Server Components + Server Actions |
| UI | shadcn/ui + Tailwind CSS | 共享组件放入 `packages/ui` |
| 数据库 | PostgreSQL | 本地和服务器均由 Compose 提供或连接托管实例 |
| ORM | Prisma | schema、迁移、seed 统一放入共享 db 包 |
| 编排 | Docker Compose | 至少包含应用服务、Postgres、迁移或初始化流程 |
| 部署 | CI + SSH 远程服务器 | CI 连接服务器后拉取项目并重新部署 |
| 鉴权 | Session/JWT 方案 | 必须支持角色和中台/后台权限保护 |

### 7.2 推荐仓库结构

```text
apps/
  storefront/        # 顾客前台 Next.js
  merchant/          # 商家中台 Next.js
  admin/             # 管理员后台 Next.js
packages/
  ui/                # shadcn/ui 二次封装与设计 token
  db/                # Prisma schema、client、migration、seed
  auth/              # 登录、会话、角色权限
  config/            # eslint、tsconfig、tailwind 共享配置
  types/             # 共享业务类型
infra/
  compose.yaml       # Compose 编排
  nginx/             # 可选反向代理配置
docs/
  PRD.md             # 本文档
```

### 7.3 部署要求

- CI 在主分支合并后执行安装、lint、typecheck、测试、构建。
- CI 通过 SSH 连接指定服务器，进入项目目录执行 `git pull`。
- 服务器执行 Prisma 迁移：`prisma migrate deploy`。
- 服务器执行 Docker Compose 重新构建和启动：`docker compose up -d --build`。
- 部署不得依赖本地机器手工复制文件。
- 环境变量不得提交仓库，必须通过服务器 `.env` 或 CI Secret 管理。

## 8. 业务状态模型

### 8.1 商家申请状态

```text
DRAFT -> SUBMITTED -> APPROVED -> ACTIVE
SUBMITTED -> REJECTED
ACTIVE -> FROZEN -> ACTIVE
```

- `DRAFT`：商家填写中。
- `SUBMITTED`：已提交，等待管理员审核。
- `APPROVED`：审核通过，生成店铺。
- `REJECTED`：审核驳回，记录原因，可重新提交。
- `ACTIVE`：店铺正常经营。
- `FROZEN`：管理员冻结，商品不可继续销售。

### 8.2 商品状态

```text
DRAFT -> ACTIVE -> OFF_SHELF
ACTIVE -> SOLD_OUT
SOLD_OUT -> ACTIVE
```

- `DRAFT`：商品未发布。
- `ACTIVE`：前台可见可购买。
- `OFF_SHELF`：商家主动下架。
- `SOLD_OUT`：库存为 0 自动下架或不可购买。

### 8.3 订单状态

```text
PENDING_PAYMENT -> PAID -> TO_SHIP -> SHIPPED -> DELIVERED -> COMPLETED
PENDING_PAYMENT -> CANCELLED
PAID/TO_SHIP/SHIPPED/DELIVERED -> AFTER_SALE
```

- `PENDING_PAYMENT`：订单已创建，等待虚拟支付。
- `PAID`：虚拟支付成功。
- `TO_SHIP`：等待商家发货。
- `SHIPPED`：虚拟运单已生成，运输中。
- `DELIVERED`：顾客确认收货。
- `COMPLETED`：评价或售后周期结束。
- `CANCELLED`：订单取消。
- `AFTER_SALE`：存在售后处理中。

### 8.4 售后状态

```text
REQUESTED -> APPROVED -> RETURNING -> REFUNDED -> CLOSED
REQUESTED -> REJECTED -> CLOSED
```

## 9. 功能需求

### REQ-001 账号注册、登录与会话

优先级：Must

系统必须支持手机号或邮箱注册、登录、退出登录和会话保持。登录后根据角色进入对应端，访问受限页面时必须校验权限。

验收标准：

- [ ] 游客可注册为顾客账号。
- [ ] 用户可使用手机号/邮箱 + 密码登录。
- [ ] 密码必须加密存储，不得明文保存。
- [ ] 未登录访问购物车、订单、中台、后台时跳转登录或返回 403。
- [ ] 不同角色只能访问授权范围内的数据和页面。

### REQ-002 顾客个人资料

优先级：Must

顾客必须能维护昵称、联系电话、默认收货地址。

验收标准：

- [ ] 顾客可查看和编辑个人资料。
- [ ] 默认地址在结算页面自动带入。
- [ ] 必填字段缺失时显示表单错误。

### REQ-003 商品发现与搜索

优先级：Must

顾客必须能浏览上架商品，按关键词搜索商品、店铺或订单号，并可按分类筛选。

验收标准：

- [ ] 首页展示上架商品卡片。
- [ ] 商品卡片展示图片、名称、卖点、价格和加入购物车按钮。
- [ ] 搜索关键词可匹配商品名称、描述、店铺名称。
- [ ] 下架、冻结商家、库存为 0 的商品不得作为可购买商品展示。

### REQ-004 商品详情

优先级：Must

顾客必须能查看商品详情，包含主图、价格、店铺、库存、参数、评分、预计发货、退换货说明。

验收标准：

- [ ] 商品详情可从首页商品卡进入。
- [ ] 商品详情可加入购物车或立即购买。
- [ ] 库存不足时禁止购买并展示原因。

### REQ-005 购物车管理

优先级：Must

顾客必须能把商品加入购物车，修改数量，删除商品，并查看金额汇总。

验收标准：

- [ ] 加入购物车后数量和导航角标更新。
- [ ] 修改数量时小计和合计实时更新。
- [ ] 数量不得小于 1，不得超过库存。
- [ ] 顾客只能查看和管理自己的购物车。

### REQ-006 结算与虚拟支付

优先级：Must

顾客必须能从购物车或立即购买进入结算页，确认地址、商品、金额，并完成虚拟支付。

验收标准：

- [ ] 提交结算后生成订单、订单项和虚拟支付流水。
- [ ] 虚拟支付成功后订单进入 `TO_SHIP`。
- [ ] 虚拟支付失败时订单保持 `PENDING_PAYMENT` 并可重试。
- [ ] 支付结果必须有弹窗或 Toast 反馈。

### REQ-007 顾客订单与虚拟物流

优先级：Must

顾客必须能查看订单列表、订单状态、虚拟运单号和物流时间线。

验收标准：

- [ ] 订单列表展示订单号、商品、状态、运单号、金额和操作。
- [ ] 商家生成虚拟运单后，顾客侧订单状态更新为运输中。
- [ ] 物流时间线展示至少 3 个节点：已发货、运输中、待确认收货。

### REQ-008 确认收货

优先级：Must

顾客必须能对已发货订单确认收货。

验收标准：

- [ ] 仅 `SHIPPED` 订单可确认收货。
- [ ] 确认后订单进入 `DELIVERED` 或 `COMPLETED`。
- [ ] 确认后出现评价入口。

### REQ-009 商品评价

优先级：Must

顾客必须能对已购买且已确认收货的商品提交评分和评价内容。

验收标准：

- [ ] 评价绑定订单项和商品。
- [ ] 同一订单项默认只允许评价一次。
- [ ] 商品详情展示评分统计和评价列表。

### REQ-010 退换货申请

优先级：Must

顾客必须能对符合条件的订单发起退货退款、换货或仅退款申请。

验收标准：

- [ ] 售后申请包含订单、商品、售后类型、原因、说明和可选凭证。
- [ ] 提交后售后状态为 `REQUESTED`。
- [ ] 商家中台能看到并处理该售后。

### REQ-011 商家开店申请

优先级：Must

用户必须能提交商家开店申请，包含店铺名称、经营类目、店铺介绍、资质图片。

验收标准：

- [ ] 未登录用户需先登录再提交申请。
- [ ] 一个用户同一时间只能存在一个待审核申请。
- [ ] 申请提交后进入管理员审核队列。
- [ ] 审核通过后生成店铺并授予商家权限。

### REQ-012 店铺管理

优先级：Must

审核通过的商家必须能维护自己的店铺信息。

验收标准：

- [ ] 商家可编辑店铺名称、介绍、类目和店铺状态展示信息。
- [ ] 商家只能编辑自己的店铺。
- [ ] 冻结状态下商家不可发布新商品。

### REQ-013 商品发布与编辑

优先级：Must

商家必须能创建、编辑、上架、下架自己的商品。

验收标准：

- [ ] 商品包含名称、价格、库存、描述、分类、图片。
- [ ] 商品价格必须大于 0，库存必须为非负整数。
- [ ] 商品发布成功后可在顾客前台展示。
- [ ] 商家不能编辑其他店铺商品。

### REQ-014 商品图片上传

优先级：Should

商家应能上传商品图片，图片用于商品列表卡片和详情主视觉。

验收标准：

- [ ] 支持 JPG/PNG。
- [ ] 单张图片大小应有限制。
- [ ] 上传失败时显示明确错误。
- [ ] 无图片商品使用占位图，不影响页面布局。

### REQ-015 商家订单处理

优先级：Must

商家必须能查看自己商品产生的订单，并处理待发货订单。

验收标准：

- [ ] 商家订单列表展示订单号、顾客、商品、状态、虚拟运单和操作。
- [ ] 商家只能查看包含自己店铺商品的订单项。
- [ ] 待发货订单可生成虚拟运单。

### REQ-016 虚拟运单生成

优先级：Must

商家必须能为待发货订单生成虚拟运单号，并推动订单进入运输状态。

验收标准：

- [ ] 运单号格式统一，例如 `VL-0000-0000`。
- [ ] 生成运单后订单状态变为 `SHIPPED`。
- [ ] 同一订单项不得重复生成多个有效运单。
- [ ] 顾客订单页可看到运单号和物流节点。

### REQ-017 商家售后处理

优先级：Must

商家必须能查看并处理顾客退换货申请。

验收标准：

- [ ] 商家可通过、驳回售后申请并填写处理说明。
- [ ] 售后状态变化必须同步给顾客订单。
- [ ] 售后处理必须记录操作日志。

### REQ-018 商家销售统计

优先级：Should

商家中台应展示待发货订单数、售后待处理数、本月虚拟销售额。

验收标准：

- [ ] 指标来自真实订单数据聚合。
- [ ] 指标仅统计当前商家。

### REQ-019 管理员平台总览

优先级：Must

管理员后台必须展示平台关键指标和待办事项。

验收标准：

- [ ] 展示入驻商家数、待审核商家数、广告位数、系统健康度。
- [ ] 待办事项可跳转到对应管理页面。

### REQ-020 商家审核管理

优先级：Must

管理员必须能审核商家申请，并管理商家启用、冻结和复核。

验收标准：

- [ ] 待审核申请可通过或驳回。
- [ ] 驳回必须填写原因。
- [ ] 通过后创建店铺并赋予申请人商家角色。
- [ ] 冻结商家后其商品不可购买。

### REQ-021 首页与广告位管理

优先级：Must

管理员必须能维护首页主 Banner、广告位、推荐分类和运营专题。

验收标准：

- [ ] 管理员可编辑 Banner 标题、图片、跳转链接、上线状态。
- [ ] 顾客首页展示已上线内容。
- [ ] 保存配置后有明确反馈。

### REQ-022 系统维护配置

优先级：Must

管理员必须能查看和维护基础系统配置。

验收标准：

- [ ] 可配置会员注册开关。
- [ ] 可配置商家入驻是否需要人工审核。
- [ ] 可刷新首页缓存或触发首页内容更新。
- [ ] 可查看虚拟支付和虚拟运单服务状态。

### REQ-023 审计日志

优先级：Should

系统应记录管理员登录、商家审核、订单发货、售后处理、系统配置修改等关键操作。

验收标准：

- [ ] 日志包含操作者、角色、动作、对象、结果、时间、IP 或请求来源。

### REQ-024 全局搜索

系统可提供统一搜索入口，根据当前端展示商品、订单、商家或运单结果。

## 11. API 与交互约束

- 业务写操作优先通过 Server Actions 或 Route Handlers 实现，必须校验登录态、角色和资源归属。
- 所有表单必须同时做前端校验和服务端校验。
- 金额统一使用整数分或 Decimal 类型，禁止用 JavaScript 浮点数直接持久化金额。
- 列表接口必须支持分页，后台和中台表格必须支持状态筛选。
- 文件上传必须校验类型和大小。课程范围内可使用本地挂载目录或对象存储兼容接口。
- 所有业务错误必须返回可展示的中文错误信息，不暴露堆栈、数据库连接串或密钥。

## 12. 非功能需求

### 12.1 性能

- 首页首屏商品列表在本地开发环境下 1 秒内完成服务端渲染或加载。
- 后台表格默认分页大小不超过 20。
- 商品图片必须使用 Next.js 图片优化或等效方案。

### 12.2 安全

- 密码使用 bcrypt、argon2 或同等级算法加密。
- 所有中台、后台页面必须做服务端权限校验。
- 管理员和商家关键操作必须记录审计日志。
- 环境变量和服务器密钥不得提交仓库。

### 12.3 可用性

- 关键操作均有加载、成功、失败状态。
- 移动端可完成顾客核心链路。
- 表单错误显示在对应字段附近。

### 12.4 可维护性

- 共享 UI、权限、数据库访问逻辑不得在三端重复散落。
- Prisma schema 变更必须配套 migration。
- 业务状态枚举必须集中定义并在前后端共享类型。

### 12.5 测试

- 公共函数、权限判断、金额计算、状态流转必须有单元测试。
- 顾客购物主链路、商家发货、管理员审核必须有端到端或集成测试。
- 目标覆盖率 80% 以上；若无法达到，必须在交付说明中列出缺口。

## 13. 种子数据要求

- 至少 1 个售后申请和 2 条评价。
- 至少 2 个首页 Banner 或广告位。

## 16. 最终交付定义

项目只有同时满足以下条件才视为完成：

- 顾客、商家、管理员三端核心页面均可访问，且与原型风格一致。
- 作业要求中的每一项功能均能用真实页面操作演示。
- 购物、开店、审核、发货、评价、售后五条主链路全部跑通。
- 第 6 章定义的 UI 页面清单、交互逻辑基线、组件状态覆盖、视觉质量门禁和自动化校验全部通过。
- 每个核心页面均有桌面端和移动端验收截图，截图中不得存在明显遮挡、溢出、错位或空白主内容。
- 数据持久化到 PostgreSQL，Prisma migration 可从空库重建。
- `docker compose up -d --build` 可启动完整系统。
- CI 能在服务器上完成拉取、迁移、重建和重启。
- README 提供本地启动、测试、部署和演示账号说明。
